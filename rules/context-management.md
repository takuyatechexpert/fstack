# コンテキスト管理

## セッション運用ルール

- コンテキスト使用量が **150K トークン** 付近で `/handover` を実行し、次セッションへ移行する
- **200K トークン** に到達させない。1M 窓のモデルでは自動圧縮が走るのは遅いが、その前に文脈劣化（判断のブレ・前提の取り違え・細かい判断理由の喪失）が進む。基準は窓に対する % ではなく絶対トークン数で持つ
- 引き継ぎドキュメント作成自体がコンテキストを消費するため、余裕を持って開始する
- セッション途中の `/model` 切替は、モデルごとに別のプロンプトキャッシュを持つため、切替後最初のリクエストで会話全体を非キャッシュで読み直す。モデルを替えるなら作業の区切りで `/handover` し、新セッションで替えるのを基本にする

## コンテキスト節約

- 広域の検索・解析で結論だけ欲しい場合はサブエージェントに委譲し、長大なツール出力をメインに持ち込まない（委譲の判断基準は下記「ツール使用方針」）
- 冗長なツール出力を避ける（`--stat` や `--oneline` オプションを活用）
- 不要なファイル読み込みを避ける（LSP を優先）

## ツール使用方針

- **並列実行を積極的に使う** — 独立した調査（複数ファイルの Read、複数シンボルの LSP 検索、複数の Grep）は単一メッセージ内で並列発行する
- **サブエージェント委譲の判断基準** — 委譲はコストが高い（各エージェントが文脈を再構築し、報告を読み直す往復が発生する）。払う価値が明確な場合に限る:
  - 広域調査で読むファイルが多く、結論だけ欲しい → `Explore` サブエージェント
  - **独立性が高くサイズのある**作業を並行で進めたい → 複数 `Agent` を単一メッセージで起動
  - 単一ファイル・単一シンボルの確認、数回のツール呼び出しで終わる作業 → 直接 Read/LSP（委譲しない）
  - **検証・裏取りには使わない** — 検証はメインループで検証コマンドを実行して行う
  - 1 体で足りるなら 1 体にする（同時上限は下記「サブエージェント同時 spawn 上限」）
- **委譲時のプロンプト構成** — 意図・制約・受け入れ基準・関連ファイル・検証手段の5点を最初のターンで揃える
- **ツール結果が長大になる場合** — サブエージェントに委譲してメインコンテキストを保護する

## サブエージェント同時 spawn 上限

| 委譲の種類 | 同時上限 |
|---|---|
| 書き込みを伴う（実装・修正） | 4 体 |
| 読み取り専用（レビュー・調査） | 6 体 |
| 絶対上限（種類を問わず） | 10 体 |

- **上限の根拠** — サブエージェントは API 呼び出しなので、マシンの CPU コア数は上限の根拠にならない。上限を決めるのは (1) 設計契約・前提を全員に同期するコスト、(2) 各エージェントの文脈再構築と報告の読み直しで増えるトークン、(3) API のレート制限と同時リクエスト数。10 体を超えると同期漏れと報告の読み落としが目立ち、並列化の利得をトークン増が相殺する
- **書き込み系を低く抑える理由** — 同一ファイルの編集競合と、設計契約・前提の同期コストが spawn 数に対して非線形に増える
- **1 体で足りるなら 1 体**。Wave や枠を埋めるための増員はしない
- **サブエージェントは孫を spawn しない** — タスク数 × worker 数でエージェントが増え続けるのを防ぐ
- **機械的に縛るなら環境変数** — `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`（`1` で孫を spawn しない。既定は 3 層）と `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`（同時数。既定 20）が使える（Claude Code 2.1.217 以降）
- **検証のために増やさない** — 検証はメインループでコマンドを実行すること（`rules/implementation-flow.md`「検証体制を足す判断」）

各スキルの実効値: `/orchestra-of-agents` 同時 4 体（5 体目は遅延 spawn） / `/review-all-pending` 5 件バッチ（バッチ完了を待って次を起動）

## Deferred Tools と ToolSearch

Claude Code では一部ツールが **deferred**（schema 未読込）状態で提供される。
セッションごとに初回利用前に `ToolSearch` で schema を取得する必要がある。

### よく使う deferred tool

| 用途 | tool 名 |
|---|---|
| タスク管理 | `TaskCreate` `TaskUpdate` `TaskList` |
| 構造化質問 | `AskUserQuestion` |
| Web取得 | `WebFetch` `WebSearch` |
| LSP 全般 | `LSP` |
| プラン管理 | `EnterPlanMode` `ExitPlanMode` |

### ToolSearch の使い方

- `ToolSearch(query: "select:TaskCreate,TaskUpdate")` — 名前指定
- `ToolSearch(query: "+web fetch")` — キーワード検索

### 取得タイミング

- 投機的に全部取らない（context を消費する）
- 必要になった時点で必要な分だけ取得
- 同じセッション内で1度取得すれば再利用可能
