# 実装フロー

## 原則

実装タスクは規模に応じて **`/solo-with-verifier`** または **`/orchestra-of-agents`** スキルの起動を検討する。小〜中規模なら単独実装でよい。

Claude 5 系（Opus 5.5 / Fable 5.1 など）は指示がなくても自己検証がモデル側に入る。検証エージェントを常時挟むと過剰検証（同じ確認の重複・トークン増）になるため、検証体制は **規模が大きく取りこぼしのコストが高い場合に限って** 足す。

一方 **スコープはモデル任せにせず明示的に縛る**（下記「スコープとテストの範囲」）。自律性が高いぶん、頼まれていない修正・拡張・余計なテストのコミットが混ざる側に振れる。

## スコープとテストの範囲（必須）

実装・修正の依頼を受けたら、明示されていなくても次を守る。タスク委任・スキルのプロンプトにも、この除外指示を最初から入れる。

- 作業中・テスト中に **既存バグ・性能懸念・タスクに書かれていない挙動** を見つけても、依頼された挙動がそれ無しに動かない場合を除き、この変更では直さない・最適化しない・拡張しない。完了報告に「フォローアップ」として書く
- タスクが曖昧なら、文言と周辺コードが最も直接支持する解釈を 1 つ選んで実装し、その前提を完了報告に書く。別解釈のぶんまで作らない
- 検証の方法は自由。使い捨てのスクリプト・簡易チェックは残さない
- テストをコミットするのは、タスクが求めている場合か、このリポジトリが同種の変更にテストを置いている場合だけ。分量は隣接するテストファイルに揃え、使い捨てチェックを恒久的なテストファイルに昇格させない
- `rules/testing.md` の TDD・再現テスト・テストケース設計（正常系・異常系・境界値）は依頼された挙動に対するもので、ここで抑える「余分」ではない。抑えるのは依頼外の挙動へのテストと、使い捨てチェックの恒久化。TDD で書いたテストも、コミットするかは上の条件で決める（条件に当たらなければ検証に使い、完了報告で触れる）
- これは「余分」を抑える話であり、**依頼された挙動はすべて完全に実装する**

## 規模別の使い分け

| 規模 | 進め方 |
|---|---|
| typo 1 行 / 設定 1 行 / コメント変更 | 単独実装 |
| 1〜3 ファイル / 1〜3 タスクの小〜中規模 | 単独実装。仕様が曖昧・影響範囲が読めない・取りこぼしのコストが高い場合は `/solo-with-verifier`（Implementer + Verifier を最大 3 反復） |
| 4 タスクのグレーゾーン | 下記「4 タスクの判断」参照 |
| 5 タスク以上 / 複数モジュール横断 | `/orchestra-of-agents` を推奨（Wave 方式の並列実装 + クロスレビュー + 横断レビュー） |

## 4 タスクの判断

- 互いに**依存があり直列的** → 単独実装、または `/solo-with-verifier`（反復で吸収）
- **独立性が高く並列化が活きる** → `/orchestra-of-agents`
- **横断レビューが要る**（複数モジュール、共通基盤に触る） → `/orchestra-of-agents`
- 迷ったら単独実装で着手し、影響範囲が想定より広いと分かった時点でスキルに切り替える

## 検証体制を足す判断

検証エージェント（`/solo-with-verifier` の Verifier / `/orchestra-of-agents` のレビュー Wave）は、次のいずれかに当てはまるときに使う。

- 5 タスク以上、または複数モジュール横断
- 共通基盤・認証・課金など、取りこぼしのコストが高い箇所
- 仕様が外部文書（Issue / 設計書）にあり、適合確認が必要

当てはまらない場合は `rules/testing.md`「検証手段」のコマンド実行で足りる。**実際にテスト・リンタを走らせることが検証**であり、エージェントを増やすことが検証ではない。

## 運用ルール

- 「修正して」「実装して」「追加して」「直して」「リファクタして」等の実装系依頼を受けたら、まず規模を見積もる。スキルを使う場合は着手前にどちらを使うか宣言する
- 単独実装でも `rules/testing.md`「検証手段」の検証コマンドは実行する
- 規模見積りが難しい場合はユーザーに方針を確認する

## Why（このルールの背景）

- 8 ファイル変更・9 タスク規模の修正（本来 `/orchestra-of-agents` の射程）を Claude が単独で完結させ、レビュー観点の取りこぼしをユーザーから指摘された事例がある。中〜大規模実装で単独進行するとレビュー観点の取りこぼし・テスト網羅性の不足が起きやすく、5 タスク以上でスキルを推奨するのはこの事例に基づく
- 一方、スキル起動の「必須」は「推奨」に緩めた。Claude 5 系は指示なしで自己検証し、「最後に検証ステップを入れる」「サブエージェントで検証する」のような明示的な検証指示は過剰検証を招く。外しても品質は落ちないと Anthropic のプロンプティングガイドが明記しており、小〜中規模で Verifier を常時挟む構成は費用に見合わない
- スコープの節は必須にした。自己検証は削ってよいがスコープは削れない。Claude 5 系は頼まれていない修正・拡張・余計なテストのコミットに振れやすく、除外指示を入れると未依頼の追加とコミットされるテストが大幅に減り、タスク成功率は変わらない（同ガイド）
