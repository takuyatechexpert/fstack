# IaC チェックリスト（CDK / CDKTF / GitHub Actions / Ansible）

worker1 / worker2 / worker3 が IaC 差分（`cdk/` / `.tf` / `ansible/` / `.github/workflows/`）で Read する。明文化された規約は無く、全項目が実指摘（IaC 系 406 件・2026-08 分析）に基づく。

**原則**: IaC の変更はデプロイした瞬間に本番リソースの置き換え・課金・権限の開放を引き起こす。項目に明記がなくても、可用性・コスト・セキュリティ境界に影響する差分は指摘する（列挙は網羅ではない）。

## 差分の種類別の適用範囲と担当 worker

| 差分の種類 | 節 | 担当 |
|---|---|---|
| CDK / CDKTF の定義コード（`cdk/**/*.ts` / `.tf`） | §1 | worker1（構成・規約） / worker2（合成時ロジック） |
| GitHub Actions（`.github/workflows/*.yml`） | §2 | worker1（セキュリティ・運用） / worker2（トリガー条件・並行制御） |
| Ansible（`ansible/`） | §3 | worker1 |
| Makefile・シェルスクリプト | §4 | worker1 |
| Lambda ハンドラの実装コード（`cdk/lambda/` 配下等） | §5 | **worker2** |
| （上記いずれかに差分があるとき） | §6 | **worker3** |

**差分に含まれない種類の節は読まずに飛ばす。** 空振り報告は「§2〜§5 = 差分に該当なし（読んでいない）」の 1 行で足りる（2026-08-24 の IaC（CDK）PR で、差分が 100% CDK だった PR に対し 4 節中 3 節が定義上空振りした）。

**§5 は Lambda ハンドラの実装コードに差分があるときだけ発火する。** CDK 定義コードは synth 時に走るコードなので、ハンドラに差分が無ければ §5 は原理的に該当しない（同 PR で worker1 が「未確認」・worker2 が「非該当」と報告し、担当が曖昧なまま両方の空振りに落ちた）。

## 1. CDK / CDKTF

- **論理 ID の安定性**: construct 第二引数（CloudFormation 論理 ID）の変更・配列途中への要素挿入は、既存リソースの削除→再作成（ECS / ALB / VPC の不通）を引き起こす。該当差分はリソース入れ替えの影響を確認する
- **環境別設定の整合**: 環境別設定ファイル（`env/*.ts` 等）の ARN・アカウント ID・CIDR はリポジトリ内のアカウント台帳（`accounts/*.ts` 等）と突合する。TODO 残置・他環境からのコピペ・同種の複数環境（staging1〜N 等）の横並び不整合（1 環境だけ変えた理由が PR に無い）を指摘する
- **IAM・セキュリティ境界**: `actions` / `resources` が要求される操作範囲を超えていないか（削除権限の混入・readonly 化の余地）。個人情報を扱う ALB・GlobalAccelerator 併用時の ALB は内部（private）構成が原則
- **コスト影響**: GlobalAccelerator・Advanced 監視等のコストのかかる機能フラグのデフォルト有効化、CloudWatch カスタムメトリクスの dimension への非有界な動的値（IP アドレス等）を指摘する
- **命名・重複管理**: スタック / construct / バケット名・リソースタグ（環境・システム識別）が責務を反映し既存の用語表記・タグ付け慣習と揃っているか。CDK ⇔ CDKTF・base ⇔ env の二重管理は一方へ集約する。設定・スクリプトは TypeScript で統一（生 JSON / JS の新規追加・不要な `let` を避ける）
- **バージョン**: Lambda ランタイム・DB エンジン・AMI・CI の Node が最新 LTS / 推奨より不必要に古く固定されていないか
- **合成時ロジックの正当性**（worker2 担当）: Aspect の `visit()` や construct 内の条件分岐・ループ・状態キャッシュ・型キャストは、**対象の取りこぼし・二重適用・既存設定の上書き**を起こす。分岐は真偽表を展開し、対象 0 件 / 1 件 / 全件の 3 ケースを手で流す
- **合成結果が実行時に効くか**（worker2 担当）: 定義コードが設定した環境変数・レイヤー・IAM が実行時に意味を持つか。**ランタイム側が読まない値・後段で上書きされる値・自動計装と重複する手動設定は no-op** なので、設定した意図と実際の効果を分けて確認する（2026-08-24 の IaC（CDK）PR で、APM の Lambda レイヤーが自動で設定する `NODE_OPTIONS` を CDK 側でも手動設定していた no-op が採用 SHOULD になった。ハンドラコードに差分が無くても成立する観点なので §5 ではなくここで見る）
- **新規リソースの追随**: 新規 Lambda / Firehose には失敗検知の監視（CloudWatch Alarm）を対で要求する。リソース名・パラメータ名の変更は参照側（Localstack 初期化スクリプト・他 IaC 定義）への追随を確認する。バッチの新規 Command は Step Functions 定義との対応を確認する

## 2. GitHub Actions

- **セキュリティ**: サードパーティ action はタグ（`@v4`）でなくコミットハッシュで固定する。`run:` 内で `${{ }}` により外部入力（`inputs` / API 出力）を直接展開しない（スクリプトインジェクション — `env:` 経由に）。`permissions:` を明示して最小化する。`pull_request_target` は fork PR への secrets・権限露出を確認する
- **トリガー条件・並行制御**: `on:` のトリガーが意図した branch / event に絞られているか・`concurrency` の要否。matrix job の同名 `outputs` は後勝ちで上書きされ、`fromJSON()` の配列は `env:` 代入でカンマ区切り文字列化される
- **運用**: ジョブに `timeout-minutes` を設定する（ハング時の課金防止）。ワークフロー / ジョブ名は処理内容が名前から分かるように。Slack 通知ワークフロー等の担当者 ID 列挙は退職・異動済み ID の残存を確認する

## 3. Ansible

- デバイス名（`nvme1n1` 等）・パーミッション・対象パスのハードコードは環境差で壊れないか前提を確認する。誤操作で消えうるパス（`/root` 直下等）を避け、専用ディレクトリ（`/opt/scripts` 等）に置く

## 4. スクリプトの実行時空展開

- `Makefile` の `K6 ?= k6` のような変数が未定義のまま `$(K6) run` されると空展開で後続引数がコマンドとして実行される。シェル / Make 変数の未定義時の挙動を確認する

## 5. Lambda ランタイム実装（worker2 担当・ハンドラコードに差分がある場合のみ）

- **ループ内の外部 API 呼び出し**: エラー捕捉・バッチ API（PutRecordsBatch 等）の活用・リトライ設定・並列化の余地を見る
- **注入された設定をハンドラが使っているか**: 定義コード側が与える環境変数・レイヤーをハンドラが実際に読んでいるか（受け手不在の設定・自前実装との二重化）

## 6. テスト手段（worker3 担当）

worker3 は §1〜§5 に固有の担当節を持たず、差分に該当する節を **「この観点の退行を何が検知するのか」** の視点で読んでテストの有無を判定する。

- **CDK は合成結果をアサートできる**: `aws-cdk-lib/assertions` の `Template.fromStack(stack)`（`hasResourceProperties` / `resourceCountIs` / `findResources`）が標準手段として存在する。**「IaC はテストできない」を前提にしない** — 適用対象の件数・除外条件・付与されたプロパティは合成結果に現れるのですべてアサート可能
- **前例を根拠にするときは追加日を確認する**: base ブランチのテストを「前例があるのだから書けるはず」の根拠に使う場合、`git log --date=iso --diff-filter=A -- {パス}` で追加日を見る。**PR HEAD より後に追加された前例は、その PR に対する MUST の根拠にできない**（2026-08-24 の IaC（CDK）PR で、base の `cdk/test/waf.test.ts` を前例に立てた MUST が「前例の追加は PR HEAD より 3 週間後」で SHOULD に格下げされた）
- **テストを足しても CI が走らせなければ退行ゲートにならない**: 対象ディレクトリが CI のジョブ対象に含まれているかを `.github/workflows/` で確認し、含まれていなければ severity の判断に織り込む（同 PR では CI 21 ジョブが `cdk/` を一切検証していなかった。**テスト不在の指摘を補強する事実が、同時に「書いても自動検知にはならない」として severity を下げる方向にも効く**）
