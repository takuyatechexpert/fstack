# レビュー結果の出力フォーマット（Phase 6・親用）

このファイルは Phase 6 開始時に親オーケストレータが Read する。verifier が採用した指摘（confirmed / downgraded）のみを以下のテンプレートに整形する。**読み手はコードを頭に入れていない**前提で書く。1 指摘 = 1 論点に絞り、前提・補足は「背景」へ追い出す。

## 出力テンプレート

```
## PRレビュー: #{PR番号} {PRタイトル}

### 概要
- 変更ファイル数: N件 / 変更行数: +X / -Y
- 変更カテゴリ: {該当するもの}
- worker 選定: 起動 {worker1, worker2, ...} / スキップ {workerN（理由）, ...（なければ「なし」）}

### 指摘事項
#### {重要度}｜{🔵 今回の変更 | 🟡 既存の潜在問題}: {1行要約（コード前提なしで読める／20〜40文字目安）}

- **どこ**: `{パス}:{行番号}`
- **何が起きてる**: {現状を1〜2文で。コード差分の事実のみ}
- **なぜまずい**: {影響を1〜2文で。プロジェクトルール・原則名は1つに絞る}
- **どう直す**: {対応案を1〜2文で。具体的な置き換え後の形を示す}
- **背景**（任意）: {前提構造／中期論点／別PRに送る関連事項}
- **コメント提案**（PR にそのまま貼れる優しい口調・後述ルール準拠）:
  > **{重要度}: {一言要約}** 🙏
  >
  > `{パス}:{行番号}` の件です。{問題を1〜2文で}。
  >
  > ```{lang}
  > {直し方の置き換え後コード}
  > ```
  >
  > {配慮の一言（急ぎでない／ついでで／検討いただければ 等）}

### 変更漏れの可能性
### 影響範囲
### 良い点
### 総評
- **Approve 判定**: {✅ Approve 可 | ⚠️ 条件付き | ❌ 要修正}
- **判定理由**: {判定を左右した指摘を挙げて1〜2文で}
- {偽陽性チェックの透明性1行（例: verifier が N 件を裏取りし M 件を棄却/格下げ）}
- {全体の所感 1〜2文}
```

**重要度**: MUST（修正必須）/ SHOULD（改善推奨）/ NITS（軽微、任意）/ QUESTION（確認事項）

**区分**（verifier が確定した `scope` を表示）: 🔵 今回の変更（この PR の変更行・追加行が原因）/ 🟡 既存の潜在問題（base ブランチ由来で元からある問題。この PR のブロック要因にはしない）

## Approve 判定の基準

上から順に評価し、最初に該当したものを採用する。

| 判定 | 条件 |
|---|---|
| ❌ 要修正 | 🔵 今回の変更起因の MUST が 1 件以上 |
| ⚠️ 条件付き | 🔵 の MUST は 0 件だが、回答次第で MUST になり得る QUESTION が残る |
| ✅ Approve 可 | 上記以外（🔵 は SHOULD / NITS のみ、または 🟡 既存の潜在問題のみ） |

- 🟡 既存の潜在問題は判定に**含めない**。指摘本文の「どう直す」に「別 Issue / 別 PR での対応を推奨」と明記する
- この判定はレビュワー（ユーザー）の最終判断を補助する**目安**であり、GitHub 上の approve 操作を自動実行するものではない

## 書き方ルール

- 1行要約は「Interface に未使用宣言が残る」「`$csv_file` の型が `object` で契約が効かない」のように **問題そのもの** を端的に。「責務の不整合」「設計改善の余地」のような抽象語は避ける
- 「何が起きてる／なぜまずい／どう直す」は **各1〜2文**。grep結果・継承関係・PR説明引用などは「背景」へ
- 1つの指摘で複数論点を扱わない。2論点あれば指摘を分ける（軽い方は NITS / QUESTION に降格してもよい）
- **同一ルール違反が多数並ぶ場合は 1 指摘に束ねる**。「どこ」に `path:line` を全列挙し、コメント提案も束ねた単位で 1 つ（`review-checklist.md` §9-4 の網羅ゲートは束ね単位で読む）
- インラインコメント化する場合は束ねを解いて全件展開してよい
- カッコ書き・コードトークンの密度は本文1文あたり3個まで目安。超えるなら文を分ける
- **総評に偽陽性チェックの結果を 1 行で触れる**（例: 「verifier が N 件を裏取りし M 件を棄却/格下げ」）。レビューの透明性のため

## コメント提案の書き方（GitHub にそのまま貼る前提の優しい口調版）

- 各指摘に必ず付ける。本文の分析とは別に、**作者へ直接渡せる短文**として用意する
- 口調は**優しく丁寧**に。相手の実装を尊重し、断定や詰問を避ける（「〜だと安心です」「〜したいです」「検討いただければ」等）
- 構成は **①重要度ラベル＋一言 → ②場所（`パス:行`）→ ③問題を1〜2文 → ④直し方のコードブロック → ⑤配慮の一言** の順。これ以上は盛らない
- 分析の根拠説明（grep 結果・型の詳説・背景）は提案文に持ち込まず要点だけに圧縮する（5〜8行目安）
- blockquote（`>`）で囲みコピペしやすくする。絵文字は控えめに可（🙏 ☺️ 👍 程度、1コメント1〜2個まで）
- MUST は配慮文でも「対応をお願いしたいです」と必須である旨を残す。SHOULD/NITS は「急ぎではないので」「ついでで大丈夫です」等で温度感を下げる

## レビュー観点の優先度

| 観点 | 重要度 | 補足 |
|---|---|---|
| アーキテクチャ違反 / コーディングルール違反 | MUST | パターン逸脱・責務混在・プロジェクト固有ルール（worker1） |
| 仕様・計画との不整合 | MUST/SHOULD | 要求未充足・仕様逸脱・過剰実装（worker5） |
| パフォーマンス問題 | MUST/SHOULD | SQL: N+1 / count+get / EXISTS 多段 / 両側 LIKE / 関数式 WHERE。フロント: ウォーターフォール / バンドル / 再レンダー（worker2） |
| 変更漏れ | MUST/SHOULD | 対応するファイルが欠落（worker4） |
| UI・アクセシビリティ違反 | MUST/SHOULD | セマンティクス・aria・フォーカス管理・ガイドライン準拠（worker6） |
| 命名規則 / テスト品質 | SHOULD | プロジェクト命名・テスト方針との不整合（worker1, worker3） |
| 影響範囲の注意 | QUESTION | 他への波及可能性（worker4） |
| 読みやすさ等 | NITS | ベストプラクティス |
