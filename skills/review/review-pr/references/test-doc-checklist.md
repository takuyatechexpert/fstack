# 試験工程ドキュメント チェックリスト（worker8 用）

テスト項目書・テスト実施手順書・UI テスト仕様書・`.hurl` 等の追加・変更をレビューする。

原則: 期待値の正しさは文書内だけでは判定できない — 必ず原典と突合する。以下に明記がなくても、期待値・手順と原典の食い違いは指摘対象になる（列挙は網羅ではない）。

## 1. 期待値の 3 点突合

期待値（ステータスコード・レスポンス JSON・URL パス・エラーコード・ログ確認項目）を次の 3 点と突合する:

1. 対応する API 設計書の最新記載
2. 異常系仕様書（エラーコード一覧・エラー通知（Sentry 等）の要否）
3. 実挙動（実装コードの該当分岐、および PR 本文・添付に実行記録があればそれ）

食い違いは「実装バグ」か「手順書側の記載誤り・陳腐化」かまで切り分けて指摘する。**実挙動が確認できない場合は切り分け自体を QUESTION にする**（どちらが正か判断できない旨を明記し、確認を依頼する）。

## 2. 試験ケースの網羅性

- API 設計書のバリデーション条件・境界値・異常系がテストケースに揃っているか。不足は具体的なケースを提案する
- 処理失敗時に後続の副作用が発生しないこと（ロールバック・二重送信の抑止）を確認するケースがあるか

## 3. 機械的整合

- テストケース番号の連番・欠番・重複・別項目との衝突
- 境界値テストに使う入力文字列の実文字数が、記載の想定文字数と一致するか（実際に数える）
- ケースのタイトルと確認内容の矛盾・同一状況に異なる期待値を置いたケースの併存
- 更新履歴テーブル: 版番号の逆行・担当者欄の空欄・変更内容の記載漏れ・PR 作成者と異なる担当者名。**更新履歴節を様式に持つ試験仕様書（UI テスト仕様書・機能テスト仕様書など）では必ず確認する**（2026-08-23 実測: 更新履歴を持つファイルの大半が UI / 機能テスト仕様書の 2 種で、UI テスト仕様書は全件が保持していた）

## 出力

> 【テスト結果: FAIL】→ 原因 → 対応方針
