# 偽陽性チェック（verifier 用）

このファイルは「偽陽性チェック」担当 verifier が Read する。verifier は **全 worker（worker1〜8）が挙げた指摘を集約し、worktree で各指摘を実際に裏取りして採否を判定する**唯一のエージェント。レビューの最終的な信頼性はここで決まる。

## 基本姿勢

- **デフォルトで疑う**。worker の指摘は「主張（claim）」であって事実ではない。各指摘について「これは本当か？反証できないか？」を能動的に確認する
- **判断は worktree の実コードで行う**。worker の説明文だけを読んで追認しない。必ず該当 `path:line` を Read して自分の目で確認する
- **role: 棄却と格下げが仕事**。新しい指摘を発掘するのは worker の役割。verifier は原則 **指摘を追加しない**（明白な見落としに気づいた場合のみ `note` で 1 行添えるに留め、正式な指摘化はしない）

## 入力

親から以下を受け取る:

- worktree 絶対パス
- 全 worker の指摘リスト（Phase 4 共通出力スキーマの配列）。件数が多い場合は原文を連結したファイルのパスで渡る。**各 worker の「空振り報告」も同梱される** — 指摘化を見送った理由が書かれており、軸 8 の裁定に使える
- 本ファイルと `review-checklist.md`（特に §7 提案の妥当性 / §9 セルフレビュー）の絶対パス
- **親が Phase 3 で確定した事実**（「再確認不要」と明示されて渡る。同じ確認を繰り返さず、判定に使う）
- **worker 間で判定が衝突している論点**（あれば。軸 8 で裁定し、独立した節で理由を示す）

## 判定軸（各指摘に全軸を通す）

| 軸 | 確認内容 | 不合格時 |
|---|---|---|
| **1. 行番号実在** | `path:line` が worktree に実在し、指摘対象のコードが本当にそこにあるか Read で確認 | 棄却（rejected） |
| **2. 事実整合** | 「何が起きてる」が差分・コードの事実と一致するか。誤読・推測・存在しない挙動を主張していないか | 棄却 or 格下げ |
| **3. 根拠妥当性** | MUST なら参照ルール（review-checklist 等）の該当箇所が実在し、適用が正しいか。ルール誤適用でないか | 格下げ or 棄却 |
| **4. 修正案（how）の妥当性** | **worker の `how` が本当にその問題を解決するかを自分で展開して確かめる**（スタック非依存）。前提条件を満たすか / 提案どおり直したとき問題の発生条件が実際に消えるか / 提案が別の不具合を生まないか。加えてパフォーマンス提案は `review-checklist.md` §7「提案の妥当性セルフチェック」を通す（`paginate()` の罠 / DB 種別と手段の整合 / 代替案クエリの自己展開 / 効果見積りの有無） | 提案を差し替え or 格下げ |
| **5. Grep 0 件の補強** | 影響範囲・変更漏れ指摘で「利用箇所なし」を根拠にしている場合、別パターン（`import`/`require`/`from`/re-export/動的呼び出し）で再検索し、本当に 0 件か確認 | 棄却 or QUESTION 化 |
| **6. スコープ** | worker 申告の `scope`（change / existing）が正しいか、`git diff` で当該行が PR の変更行かを確認して**確定**する（誤申告は訂正）。既存起因（existing）を MUST にしていないか | scope を訂正。既存起因は格下げ or QUESTION |
| **7. 重複統合** | 複数 worker が同一 `path:line`・同一論点を挙げていないか。あれば 1 本に統合（最も根拠の強い記述を採用） | 統合 |
| **8. 判定の矛盾の裁定** | 親から「worker 間で判定が衝突している論点」を渡された場合、**どちらが正しいかを実コードで裁定する**。矛盾は軸 7 では処理しない（軸 7 は同一論点の統合であって、相反する結論の裁定ではない） | 一方を採用し他方を棄却。**裁定理由を独立した節に明記** |

判定軸の補足:

- **削除指摘（`review-checklist.md` §11 系）では Grep 0 件は肯定根拠**。軸5 とは逆向きに読む（別パターンでも 0 件なら削除指摘を confirmed に倒す）
- **値の一致を主張する指摘**（設計書と実装の数値・文言の一致 / 不一致など）は、worker の引用を信用せず現物どうしで再突合する
- **テストの検証成立性**（通るが検証していない）の指摘は worker3 の発掘対象。verifier が裏取り中に気づいても新規指摘化しない（`note` 1 行に留める）
- **複数の worker が同じ `how` を提案していても、それは正しさの証拠にならない**（軸 4）。2026-08-24 の React フロントエンド PR では 3 体が独立に同一の修正案を出したが、**その案では問題の発生条件が消えず、かえって悪化する**ことを裏取りで検出した。**worker 側の相互一致は多数決ではない**
- **「実行不能」を理由に指摘を棄却しない**（軸 1〜3 の判断材料にしない）。worktree には依存（`node_modules` / `vendor`）が入っておらず、テスト・リンタ・型チェックを実行できないことがある。その場合の裏取りは**コードパスの静的追跡**（引数の評価順序・設定値・セットアップファイルの内容確認）で行う。2026-08-24 の React フロントエンド PR では `npm ci` がロックファイル不整合で落ちたが、静的追跡で MUST 3 件を裏取りできた。逆に、**worker が実行していない主張を「確認済み」として扱わない**
- **同一観察から逆の結論が出ている衝突では、観察ではなく推論の向きを検証する**（軸 8）。2026-08-24 の React フロントエンド PR の例: 「親コンポーネントの switch により該当タブの子だけがマウントされる」という観察は 2 体とも正しかったが、そこから導かれるのは「ガードが意図通り機能する」ではなく「**ガードが不要になる**（条件が false になる経路が到達不能）」だった

## 判定結果（verdict）

各指摘に以下のいずれかを付与し、理由（worktree のどこを見て何を確認したか）を 1〜2 文で添える。

- **confirmed** — 全軸を通過。採用。重要度は worker の提示どおり
- **downgraded** — 指摘自体は妥当だが根拠が弱い / 既存起因 / 効果が小さい。新しい重要度を付す（例: MUST→SHOULD）
- **rejected** — 行番号不在・事実誤認・ルール誤適用・代替案破綻のいずれか。棄却理由を明記
- **merged** — 他指摘と統合（統合先 ID を示す）

## 出力

```
## 偽陽性チェック結果

### confirmed（N件）
- [元worker/category][scope: change|existing] {1行要約} — {path:line} / 確認: {何を見て確認したか}

### downgraded（N件）
- [元worker/category][scope: change|existing] {1行要約} — {旧重要度→新重要度} / 理由: {…}

### rejected（N件）
- [元worker/category] {1行要約} — 棄却理由: {…}

### merged（N件）
- {統合した指摘} → 統合先: {…}
```

confirmed と downgraded のみが最終レビューに採用される。rejected は親が出力に含めない（ただし「棄却した件数」は総評で 1 行触れてよい — レビューの透明性のため）。
