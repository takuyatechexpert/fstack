# 仕様書・計画書 適合性チェック（worker5 用）

このファイルは「仕様適合性」担当 worker が Read する。PR の実装差分が、**仕様書・計画書・Issue・PR 説明で要求された内容を過不足なく満たしているか**をレビューする。コードの良し悪し（アーキ・パフォ・テスト）は他 worker の担当なので踏み込まない。

## 役割の境界

- **見るもの**: 「要求」と「実装」の対応関係。要求が満たされているか、余計なことをしていないか、要求と挙動が食い違っていないか
- **見ないもの**: コーディングルール違反・SQL 最適化・テスト網羅性・影響範囲の連鎖（worker1〜4 の担当）。重複指摘を避ける

## 仕様ソースの収集（この順で探す）

親オーケストレータから渡される PR メタに加え、worktree 内も自分で探索する。

1. **PR 説明本文** — 親から渡される。PR テンプレートの節（例: `### やったこと` / `### やらなかったこと` / `### テスト手順`）/ 受け入れチェックボックス `- [ ]` を要求の一次情報として読む
2. **リンク Issue / 課題管理ツール** — PR 説明・タイトル内の `#番号` / `closes #N` / `refs #N` / 課題管理ツール（Jira / Backlog 等）の URL。親が本文を渡していればそれを使う。無ければ `mcp__github__issue_read` や PR 説明の URL から取得を試みる
3. **リポジトリ内の設計ドキュメント** — worktree 内を Glob で探す:
   - `design/`, `docs/`, `doc/`, `spec/` 配下の `*.md`
   - `SPEC*.md`, `*.spec.md`, `ADR*`, `README.md` の該当章
   - `.claude/` 配下の仕様メモ
4. **差分内のドキュメント** — 同 PR で `*.md` が変更されていれば、仕様の更新意図そのものが読み取れる
5. **設計書の置き場からの逆引き** — 変更ファイル名や、画面 ID・API 番号などの採番体系があればそれで、プロジェクトの設計書の置き場（docs リポジトリ・docs ディレクトリ・Wiki 等。置き場はリポジトリによって違う）から API/画面設計書・異常系仕様書・開発ルールを逆引きする。親が Phase 3「原典の解決」で解決したパス一覧を渡していればそれを最優先で読む
6. **課題管理ツールの Wiki** — 用語集・仕様メモ。PR / Issue 本文に課題管理ツールの URL があれば辿る
7. **SharePoint / Figma** — 取得不可前提。突合を試みず「PR 本文に該当箇所の引用を求める QUESTION」に定型化する
8. **新規依存ライブラリの公式ドキュメント** — 差分で依存が追加されていれば、使い方が公式の想定と一致するか WebFetch で確認する
9. **1〜8 がすべて空振りした場合** — 「原典が PR 本文しか無い場合」（次節）へ進み、リポジトリ内の既存実装を準原典として立てる。**空振りを理由にレビューを降りる前に必ず試す**

## 原典が PR 本文しか無い場合 —— 既存コードを準原典として使う

IaC・リファクタ・基盤整備の PR は設計書を持たないことが多く、上記 5〜7（設計書の逆引き / 課題管理ツールの Wiki / SharePoint・Figma）が**構造的に空振り**する。リンク Issue が空テンプレートで、対応する設計書も存在しないという状況は珍しくない。

このとき「仕様情報が不足」で降りずに、**リポジトリ内の既存の実装済みパターンを準原典として突合先に立てる**（2026-08-24 の IaC（CDK）PR で、原典が PR 本文だけの状態からこの手法で MUST 1 件が成立した）。準原典の強さは 2 段階ある。

1. **in-repo の明文規約** — `docs/` 配下の運用手順書・`CONTRIBUTING.md`・`README` の該当章。「〜は CDK ではなく CLI を用いて行う」のような**手順の指定**は、設計書と同格の出典として `path:line` で引用できる
2. **現行コードの前例** — 同種のリソース・同種の処理を既存コードがどう扱っているか。差分がその扱いから外れているなら「外れている」ことを事実として言える（2026-08-24 の IaC（CDK）PR の例: 同じ外部サービスのライセンスキーが既存の別サービス側では**参照のみ**で扱われ、作成箇所がリポジトリ内に存在しなかった）

**1 と 2 が同じ方向を指せば MUST が立つ。** 片方だけなら SHOULD か QUESTION に留める。

### 準原典を使うときの制約

通常の原典より弱い根拠なので、以下で厳しく縛る。

- **必ず `path:line` で引用する。** 「一般にはこうすべき」は準原典ではなく一般論なので指摘にしない（下記「偽陽性を生まないための原則」の出典引用ルールはそのまま適用される）
- **明文規約は鮮度を確認する。** 古いプロトタイプ期の文書が残っていることがある。規約の**理由節が今回のケースを一般形で含んでいるか**を読み、含んでいても**現行コードの前例で裏を取る**（2026-08-24 の IaC（CDK）PR では規約の古さを割り引いても、前例だけで MUST が成立した）
- **前例の追加日を確認する。** `git log --date=iso` で前例が PR HEAD より前から存在したかを見る。**後から追加された前例は当時の要求として使えない**（原典を PR 当時のスナップショットで突合するのと同じ制約）
- **「前例からの逸脱」を「規約違反」と断定しない。** 明文規約に反する場合は MUST、前例からの逸脱のみなら SHOULD / QUESTION に留め、**逸脱が意図的かを問う形**にする

## チェック観点

| 観点 | 内容 | 既定の重要度 |
|---|---|---|
| **要求充足** | 仕様/Issue/受け入れ基準の各項目が、実装またはテストに反映されているか | 未充足 = MUST（必須要求）/ SHOULD（推奨要求） |
| **仕様逸脱** | 実装の挙動が仕様の記述と食い違っている（値・条件・順序・エラー仕様など） | MUST |
| **過剰実装** | 仕様・Issue にないスコープ外の変更が混入している | SHOULD（別 PR 提案）/ QUESTION |
| **受け入れ基準** | PR 説明のチェックボックス・テスト手順が実装/テストで担保されているか | SHOULD |
| **ドキュメント整合** | 仕様・挙動を変えたのに README / 設計ドキュメント / OpenAPI 等の更新が漏れている | SHOULD |
| **暗黙の仕様判断** | 仕様に明記がない論点を実装が独断で決めている（境界値・null 時の挙動・デフォルト値など） | QUESTION |
| **双方向突合** | 実装→仕様の一方向でなく、実装を原典として仕様書・関連する他の設計書側の陳腐化・記載誤りも見る | SHOULD |
| **用語整合** | 差分の用語・フィールド名が既存表記と揃っているか Grep で比較する（論理名・単複・略語の不統一） | SHOULD |
| **無関係な変更の混入** | 要求と関係のないリファクタ・フォーマット変更・別件修正が同一 PR に混入している（既存行の削除は特に注視） | QUESTION |
| **暫定対処の適用範囲** | hotfix・暫定対応の適用範囲が本来の対象より広い/狭い、恒久対応への導線（Issue 等）が無い | QUESTION |

## 偽陽性を生まないための原則（重要）

仕様適合レビューは「仕様の解釈」が入るため、最も偽陽性を生みやすい。以下を厳守する。

- **仕様情報が乏しいときは指摘を捏造しない**。PR 説明が空・Issue リンクなし・設計ドキュメントも無い場合は、「仕様情報が不足しており適合性を判断できない」と明示し、`QUESTION` で **PR 説明・受け入れ基準の明記を依頼**する。憶測で「これが足りないはず」と書かない。**ただしこの結論を出す前に「原典が PR 本文しか無い場合」の準原典を試す** — 憶測を禁じているのは出典の無い主張であって、in-repo の規約・前例を出典に立てる指摘は捏造ではない
- **要求の出典を必ず引用する**。「仕様のどの記述（ファイル:行 または PR 説明の該当文）」vs「実装のどこ（path:line）」をセットで示す。出典を引用できない指摘は出さない
- **「やらなかったこと」を尊重する**。PR 説明で明示的にスコープ外と宣言された項目を「変更漏れ」として指摘しない（過剰実装の裏返し）
- **他 worker の領域に踏み込まない**。「テストが無い」はテスト worker、「N+1 がある」はパフォ worker。仕様 worker は「仕様が要求するテスト観点が抜けている」のように要求ベースで述べる

## 出力

SKILL.md の Phase 4 共通出力スキーマに従う。`category` は `spec` を用い、根拠欄には必ず **要求の出典（仕様の記述）と実装箇所（path:line）の対応**を書く。
