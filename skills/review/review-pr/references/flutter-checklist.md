# Flutter・Dart チェックリスト

Flutter・Dart 分岐の worker が Read する。担当節: worker1 → §1・§3 / worker2 → §2 / worker3 → §6 / worker5 → §4 / worker6 → §4・§5。

**方針（thin）**: 規約の本体は worktree 内の in-repo 原典（`docs/*.md`）にある。本ファイルは「原典の読み順＋原典に無い判定材料＋突合手順」だけを持ち、規約値の転記はしない（転記は陳腐化して偽陽性源になる）。**原典に明記がなくても原則に反するものは指摘する（本ファイルの列挙は網羅ではない）**。

## 1. 原典の読み順

worktree（PR head ブランチ）の `docs/` を読む。担当観点に応じて以下の順で参照する。各行は「何の判定材料か」。ファイル名は例なので、対象リポジトリの実ファイルに読み替える。

1. `docs/ARCHITECTURE.md` — パッケージ構成（`apps/app` / `packages/*`）・レイヤ責務・依存方向の正誤
2. `docs/CODING_GUIDELINES.md` — 命名・イディオム・Riverpod / freezed の使い方
3. `docs/MODELING.md` — ドメインモデル・VO / extension type / enum の設計判定
4. UI 実装ガイド — UI 実装の共通規則・共通 Widget の使い分け
5. `docs/RESPONSIVE_DESIGN.md` — 画面サイズ差・レイアウト頑健性の規約（§5 の原典）
6. 画面遷移方式の対応表 — go_router の遷移方式（`push` / `go` / `pushRelative` 等）の正誤
7. 計測設計の文書 — 計測レイヤー構成とイベント一覧（§4 の突合原典）
8. ログ収集方針の文書 — ログレベル（error = 想定外 / warning = 想定内・一時的 / info = 重要アクションのみ）の使い分け
9. `docs/TEST_POLICY.md` — テストレベル・層別の対象・命名・モック戦略（§6 の原典）
10. `docs/DOCUMENTATION.md` — dartdoc・ドキュメント記述の規約
11. custom_lint パッケージの README — custom_lint ルールの意図（lint 違反の背景理解）

- 表題が「提案書」の文書（例: ルーティングの提案書）は確定規約かを要確認。単独根拠の MUST にせず、確定版の規約（読み順 6 の遷移方式の対応表など）と併読する
- `.cursor/rules/*.mdc` は内容が薄い場合ポインタ先にしない（`docs/` を直接指す）

## 2. ロジック・非同期・並行

in-repo 原典に該当章が無い領域（明文規約なし・実指摘 89 件に基づく）。以下を直接の判定材料とする。

- **多重実行の防止**: 送信中の `onPressed: null` / in-flight フラグ / 多重 push の dedupe。連打・二重送信・二重遷移が起きない構造か
- **完了保証**: `Completer` / dio interceptor の `handler` が例外経路を含む全経路で必ず 1 回 settle されるか。失敗時の巻き戻し（楽観更新のロールバック・複数書き込みの transaction 化・独立操作は両方試行してからまとめて throw）
- **Future の合成と順序**: 依存の無い複数 `await` は `Future.wait` にまとめられないか。逆に順序保証が要る箇所の誤並列化・同一リソースへの並列書き込みが無いか
- **fire-and-forget の例外**: 返り値を使わない Future は `unawaited` で明示させ、例外が黙って消えていないか確認する
- **キャンセル伝播**: 共有状態機械の再入・同時解放・優先度・キャンセル伝播の契約が dartdoc とテストで固定されているか
- **ライフサイクル**: `build` / コンストラクタで生成した Recognizer / Controller / コールバック登録に対応する `dispose` / 解除の対称性。`await` や遅延発火コールバック後の `mounted` ガードと、参照している `context` の所有者

## 3. ネイティブ・依存・ビルド

in-repo 原典に該当章が無い領域（明文規約なし・実指摘 65 件に基づく）。

- **iOS ⇔ Android の対称性**: 同じ処理・フラグ解除・最小バージョンが両 OS に入っているか（片側だけなら指摘）。プラットフォーム間の挙動差は明文化を求める
- **Pigeon / MethodChannel のリーク**: インスタンス管理が Plugin クラスに集約され、旧インスタンスの解放とコールバックの上書き漏れが無いか
- **依存解決の整合**: 直接依存を足したのに lock が transitive のまま（`melos bootstrap` 未実行）／AGP・Kotlin 制約との両立／下位パッケージ（共通 UI パッケージ等）が上位向けライブラリへ依存を新規獲得していないか／`dependency_overrides` の固定理由
- **生成物と生成元の対応**: `*.g.dart` / `strings.g.dart` 等の生成物と生成元（i18n json・`pubspec.yaml`・`build.yaml`）の片側だけの差分を指摘する

## 4. 突合手順（Figma・計測・固有名詞）

1. **Figma は取得不能**: **本スキルの実行環境から Figma 本体は開けない**（2026-08-23 のマージ済み Laravel PR・2026-08-24 の Flutter アプリ PR の 2 件で、worker5・worker6 とも「設計書内に Figma リンクはあるが開けない」で停止した）。ノード URL の探索に手数をかけない。**代わりに画面設計書の記述と突合する** — 表示文言・要素の有無・順序・データ取得元は設計書のテーブルに書かれており、ここは突合できる（2026-08-24 の Flutter アプリ PR の MUST 1 件目は Figma ではなく画面設計書の表示文言の指定から出た）。色・余白・角丸の実数値のように Figma でしか判明しない項目は突合を試みず、worker5 は「PR 本文に該当箇所の引用を求める QUESTION」に定型化し、worker6 は指摘せず「Figma は取得不能・設計書側は突合済み」と親に報告する（偽陽性ガード）
2. **固有名詞の在庫化**: `packages/` 配下の共通 UI・ユーティリティパッケージを Glob して共通 Widget・ユーティリティを在庫化してから、差分の新規実装に同等物が無いか突合する（Glob / grep のヒット行を evidence にする）
3. **計測**: 差分に計測 SDK（`FirebaseAnalytics` 等）/ `*AnalyticsEvent` が含まれる場合、計測設計の文書（§1 の読み順 7）のイベント一覧と突合する（パラメータの設定値ルール・発火箇所の対応・未配線の検出）

## 5. UI・レイアウト頑健性

- 原典は `docs/RESPONSIVE_DESIGN.md` と UI 実装ガイド（§1 の読み順 4・5）
- **タップ領域**: 48pt 未満になる padding / constraints / `isDense` 等の指定（Material 推奨 48・最低 32pt。明文規約なし・Material ガイドラインと実指摘に基づく）
- **小画面での溢れ**: 最小幅（`docs/RESPONSIVE_DESIGN.md` が対象デバイスとして定める最小幅）で溢れる固定高・固定幅・折り返しを考慮しない `Row`。**判定の前に同ドキュメントのスケール方針を読む** — 何がスケールし何がスケールしないかは原典が定義しており、そこで「対応しない」とされている軸を根拠にした指摘は成立しない（2026-08-24 の Flutter アプリ PR で、本ファイルが挙げていた OS フォント拡大＝`TextScaler` の観点が原典の「対応しない」と衝突し、worker6 が方針上対象外として落とした）
- **AsyncValue 表示・Autofill・システム戻るは明文規約なし** — 一般ベストプラクティスで判定していることを指摘に明示する（severity は SHOULD 以下が目安）
- **実機依存の挙動**（実機 / エミュレータでしか判明しないもの）は断定せず QUESTION 止まりにする
