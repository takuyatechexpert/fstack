# 設計書レビューチェックリスト（worker7 用）

設計書（API 設計書・画面設計書・テーブル定義書・機能設計書・異常系仕様書・OpenAPI YAML）の追加・変更をレビューする。設計書の置き場（docs リポジトリ・docs ディレクトリ・Wiki 等）はリポジトリによって違う。

原則: 設計書の品質基準は「読者が実装・試験の判断を誤らないこと」。以下の節に明記がなくても、記載と現物（原典・実装・他設計書）の食い違いは指摘対象になる（列挙は網羅ではない）。規約値はこのファイルに転記しない — 設計書の置き場にある兄弟設計書・テンプレート・項目名の統一表を原典として引く。

## 1. 機械チェック（最初に実行し、出力を evidence にする）

目視の checklist 項目ではなく、worktree でツールを実行して出力をそのまま evidence に使う。**ツールが無い・実行に失敗した場合はスキップし、その旨を親への報告に必ず含める**。

- `markdownlint <変更した .md>` — 表崩れ・列ズレ・見出しレベル・書式（GitHub でのレンダリング崩れ）
- `redocly lint <OpenAPI .yaml>` — OpenAPI 記法。手動観点（実指摘に基づく）: `$ref` はプロジェクトで決めた共通定義ファイルの components を経由する / 重複定義を作らない / `properties.data.example` 等の不要記述・未定義変数を残さない
- リンク実在: 変更ファイル内の相対パス・GitHub URL・Figma node-id を抽出し実在を確認（`lychee` 等があれば使う。無ければ Glob / WebFetch で個別確認）。テンプレートのコピペで**別画面の node-id・ブランチ違いの URL** が残る事故が頻出

## 2. 文章表現・テンプレート適合（兄弟比較で判定する）

設計書の置き場にある**同種の兄弟設計書・テンプレートを 2〜3 件 Read し、比較して**判定する（規約の転記はしない）:

- 文体（ですます/である調）・見出しの構成と順序・パラメータ表の列構成が兄弟と揃っているか
- ヘッダメタ情報・ファイル名・API 番号（採番体系があれば）が API 一覧・命名規則と一致するか
- typo（カラム名・テーブル名のスペルミス）・実態と異なる例示（架空値・古い値）
- 1 ファイルへの複数関心の混在・関連記載の分散重複・共通処理の重複記載（分割・統合・共通設計書への参照統一を提案）

## 3. ファイル内の自己整合

- 「取得元」欄が指すステップ番号・オブジェクトパスを実際に辿り、シーケンス図・処理手順の番号と一致するか（桁位置・ネスト位置の誤り・記述の途中切れ）
- Mermaid（sequenceDiagram / flowchart）の participant・矢印の有無と方向・分岐・終端条件が本文の処理概要・条件式と一致するか。欠けている枝（エラー時の操作可否・ページング終端）
- レスポンス例のサンプル値が仕様上あり得ない値・非統一な値（日付フォーマット・ID・改行エスケープ）になっていないか
- 更新履歴テーブル: 版番号の逆行・担当者欄の空欄・変更内容の記載漏れ・PR 作成者と異なる担当者名。**更新履歴節を持つ設計書に限る** — 原典テンプレートに更新履歴節の定義が無い種類の設計書では、節が無いこと自体は指摘対象にしない（2026-08-23 実測: テンプレートに定義が無い種類の API 設計書には、節を持つものが 1 件も無かった）

## 4. 他ファイルとの整合

- 画面設計書の「データ取得元」列・表示項目一覧が参照する API レスポンスのフィールドパス・API 番号が、API 設計書のレスポンス定義に実在するか（ID 重複・コピペ残りに注意）
- 同一仕様を記述する別設計書（BFF⇔バックエンド・兄弟画面・README/手順書）への追随 — 手順は `impact-check-rules.md` §15「設計ドキュメントが変更された場合」
- 用語・論理名・フィールド名の統一: 既存の表記を Grep で比較する。統一表記は項目名の統一表等の原典があればそれを引く（対応表をここに転記しない）
- ファイル名・見出しの Unicode 正規化（NFD 由来の濁点分離）が混入していないか

## 5. 既存実装との逆方向突合

設計書に記載された処理内容・データソース・取得条件・SQL・カラム名を、実装コード（実装リポジトリ（バックエンド / BFF 等）の該当箇所）と突き合わせ、**設計書側が実装を正しく記述していない**箇所を実装ファイルのパス付きで指摘する。実装リポジトリが手元に無ければ `mcp__github__get_file_contents` で該当ファイルのみ取得する。

## 6. 残留記述の掃除

変更で不要になった旧仕様の記述（注記・分岐説明・削除済み画面への参照）・TBD 等の未確定プレースホルダ・実装が変われば形骸化する記載（SQL 例）が残っていないか。削除を指摘する。

## 7. アーキテクチャ設計（設計書段階の指摘）

非同期処理・キュー設計・レイヤ責務・API 粒度について、既存の仕組みで代替できる複雑さ・責務の重複・バックエンド/BFF 間の整形責務の置き場の誤りがあれば、簡素化案を添えて指摘する（実装前の議論なので断定せず SHOULD / QUESTION 中心）。

## 出力

SKILL.md の Phase 4 共通出力スキーマに従う。`category` は `doc` を用い、根拠欄には「設計書の記述（path:line）」と「突合した現物（原典・実装・兄弟設計書の path:line、または lint 出力）」の対応を書く。
