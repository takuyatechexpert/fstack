# build-planner

実装に着手する**前段**を担うスキル。「何を・どう作り・どの粒度で実装に入るか」を整理し、最終成果物として `docs/plans/{機能名}.md`（計画書）を出力する。
この計画書を起点に、後段の `solo-with-verifier` / `orchestra-of-agents` がそのまま実装を開始できる。

## 位置付け

| スキル | 担当フェーズ |
|---|---|
| **`build-planner`（本スキル）** | 設計・仕様・計画書・粒度判定（実装の**前**） |
| `solo-with-verifier` | 1〜3ファイル・1〜3タスクの実装 |
| `orchestra-of-agents` | 5タスク以上・複数モジュール横断の実装 |

連携は **`docs/plans/{機能名}.md` という成果物ファイル経由の疎結合**で行う。
本スキルはスキル間の直接参照や SSOT 共有をせず、計画書という中間生成物だけを後段に渡す。

## 参照ファイル（Phase 4 で Read）

- **計画書テンプレート**: `${CLAUDE_SKILL_DIR}/references/plan-template.md`

要約・メモリからの再現は禁止。出力直前に必ず Read して使う。

## ワークフロー

### Phase 1: 意図・ゴールの確認

実装で達成したいことをユーザーと握る。曖昧なまま進めると後段の計画書がブレるため、ここで固定する。

- **意図**: 何を達成したいか（ビジネス目的・ユーザー価値）
- **完了条件**: どうなれば完成か（受け入れ基準の種）
- **制約**: 使ってよい技術・守る規約・触ってはいけない範囲
- **機能名**: 計画書のファイル名 `docs/plans/{機能名}.md` に使う kebab-case の名前

不明点が残るなら、ここで質問して解消してから次へ進む。

#### Why: 計画書は後段スキルの「契約書」になる。入口の意図が曖昧だと、設計・タスク分解・粒度判定すべてが下流で破綻する。

### Phase 2: 既存コード調査・影響評価（architect へ委譲）

`architect` エージェント（読み取り専用の設計分析エージェント）を spawn し、影響範囲とアーキテクチャ評価を依頼する。

- 委譲時に渡す: Phase 1 の意図・完了条件・制約・関連しそうなディレクトリ
- architect の出力: 現状の構造 / 変更影響範囲（ファイル×影響度）/ 実装方針2案以上（推奨明示）/ リスク
- Claude 本体で grep を撒くより、読み取り専用エージェントに調査を閉じ込めてコンテキストを節約する

#### Why: 推奨方針を出す前に影響評価を済ませることが目的。調査を後回しにして先に「最終設計」を提示すると、後から影響が判明して手戻りする（このスキル誕生の直接原因となった反省）。

### Phase 3: 設計・仕様の確定

architect の方針を踏まえ、実装に必要な設計契約を確定する。orchestra Wave 0 と**互換の4項目**を必ず埋める。

1. **エンティティ関係図**: 主要な型・構造体の関係と ID の流れ
2. **モジュール境界の API**: モジュール間の呼び出しインターフェース（関数シグネチャ + 戻り値の意味）
3. **データフロー**: イベントがどの順序でどのモジュールを通るか
4. **共有型の定義場所**: どの型をどこに置くか、重複定義の禁止ルール

この4項目は plan-template.md の見出しと一対一で対応している。

#### Why: orchestra-of-agents は Wave 0 で同じ4項目の設計契約書を作る。互換フォーマットにしておけば、計画書を Wave 0 の成果物としてそのまま流用でき、二重作業を避けられる。

### Phase 4: 計画書を出力

`${CLAUDE_SKILL_DIR}/references/plan-template.md` を Read し、Phase 1〜3 の内容を埋めて `docs/plans/{機能名}.md` に書き出す。

- 出力先ディレクトリが無ければ `mkdir -p docs/plans` で作成する
- メタ情報・設計契約4項目・タスク分解（Wave/順序・並列可否）・受け入れ基準・検証手段をすべて埋める
- 粒度判定結果の欄は Phase 5 で確定してから記入する

#### Why: テンプレートを毎回 Read するのは、後段の orchestra がそのまま流用できる見出し構成を確実に揃えるため。記憶から再現すると見出しがズレて互換性が壊れる。

### Phase 5: 粒度判定して実装スキルへ引き渡し

計画書のタスク分解を以下のルーブリックに当てはめ、引き渡し先を決める。

| 引き渡し先 | ファイル数 | タスク数 | 依存・影響範囲 | 設計判断 |
|---|---|---|---|---|
| **直接実装** | 1（typo / 1行） | — | なし | 不要 |
| **`solo-with-verifier`** | 1〜3 | 1〜3 | 単純（直列・独立）・単一モジュール | 既存パターンに沿う |
| **`orchestra-of-agents`** | 4以上 | 5以上 | Wave設計が必要・複数モジュール横断 | アーキテクチャ選択を要する |

**判断軸**: ファイル数・タスク数・依存関係（並列化が活きるか）・影響範囲（単一/横断）・設計判断の重さ。
いずれか1つでも上位条件に該当したら上位スキルへ寄せる（安全側）。4タスクのグレーゾーンは、独立性が高く並列化が活きる/横断レビューが要るなら orchestra、依存が直列なら solo に倒す。

判定後、計画書のパス `docs/plans/{機能名}.md` を着手起点として後段スキルへ引き渡す。後段は計画書を Read して実装を開始できる。

#### Why: build-planner 自身が粒度判定を提供しながら、その実装を単独で済ませて Verifier を入れない、という自己矛盾を避けるための明文化。判定基準を表で固定し「自分でやった方が早い」で直接実装に逃げない。

## 出力フォーマット（引き渡し時）

```markdown
## build-planner 完了
### 機能名: {機能名}
### 計画書: docs/plans/{機能名}.md
### 設計契約: エンティティ関係図 / API境界 / データフロー / 共有型 すべて記入済み
### 粒度判定: {直接実装 | solo-with-verifier | orchestra-of-agents}
- 根拠: ファイル{N} / タスク{N} / 依存{単純|Wave} / 影響{単一|横断}
### 引き渡し: 「docs/plans/{機能名}.md を起点に実装してください」で後段スキルへ
```

## Pitfalls（ハマりどころ）

### 1. テンプレの SSOT をスキル間で共有しようとする

**症状**: 「計画書テンプレを build-planner に置き orchestra から参照させれば DRY」と考えて移設すると、orchestra 単独起動時にテンプレが見つからず壊れる。
**Why**: `${CLAUDE_SKILL_DIR}` は起動中スキルのディレクトリに解決される。orchestra から build-planner のパスは解決できず、orchestra の自己完結性（単独起動できる性質）も失われる。
**ルール**: テンプレは両者が**互換フォーマットで各自保持**する（重複2箇所は Rule of Three 未満で許容）。連携は `docs/plans/{機能名}.md` という成果物ファイル経由の疎結合に限る。

### 2. 影響評価より先に「最終設計」を提示する

**症状**: grep / architect 調査を省いて先に推奨方針を出し、後から影響範囲が判明して設計をやり直す。
**Why**: 調査を後回しにすると、既存コードの制約・依存を知らないまま設計を固めてしまう。
**ルール**: Phase 2（architect 委譲）を必ず Phase 3（設計確定）の前に通す。推奨方針は影響評価の結果として出す。

### 3. 粒度判定を省いて計画書だけ渡す

**症状**: 計画書は作るが引き渡し先を決めず、結局 Claude が単独実装してしまう。
**Why**: 判定を曖昧にすると「自分でやった方が早い」に流れ、Verifier / クロスレビューの独立視点が入らない。
**ルール**: Phase 5 のルーブリックで必ず引き渡し先を1つ確定し、計画書の粒度判定欄に記入してから引き渡す。

## ログ記録

`~/.claude/hooks/skill-log.sh build-planner <TAG> "<message>"` で分岐ごとに記録する。

- `PLAN_DONE` "{機能名} phases=1-5 docs/plans/{機能名}.md"
- `GRANULARITY` "{機能名} verdict={direct|solo|orchestra} files={N} tasks={N}"
- `HANDOFF` "{機能名} -> {solo-with-verifier|orchestra-of-agents}"
- `ESCALATE` "{機能名} reason={要件不確定|設計判断保留}"
- `ERROR` "{エラー内容}"

> **Note**: スキル起動（START）ログは PostToolUse (Skill) hook が自動記録するため、本スキル側での記述は不要。
