# rules チェックリスト

Verifier が観点3「rules 遵守」で確認する項目一覧。
原典は fstack 同梱の `rules/` ディレクトリ（`fstack-` プレフィックス付きで `~/.claude/rules/` にインストールされる。詳細は README 参照）。各項目で違反を見つけたら該当 rules ファイルのセクションを Read で参照し、違反内容を path:line で示すこと。

---

## design-principles.md（設計原則）

- [ ] **SRP**: 1クラス/1関数 = 1責務になっているか。複数の関心事が混在していないか
- [ ] **DRY**: 同じロジックが3箇所以上に出現していないか（Rule of Three）。新規関数が既存と責務重複していないか
- [ ] **DDD / 命名**: 名前から意図が読み取れるか。汎用名（data / handle / manage）でドメイン用語を逃げていないか
- [ ] **bool プレフィックス**: `is_` / `has_` / `can_` を使っているか
- [ ] **クラス名は名詞・メソッド名は動詞** で始まっているか
- [ ] **プロパティアクセス**: setter/getter 経由と直接代入が混在していないか（一貫しているか）
- [ ] **新規プロパティに setter/getter を併設** したか
- [ ] **クリーンアーキテクチャ**: 依存方向が外→内になっているか（内側が外側をインポートしていないか）
- [ ] **関心の分離**: Gateway/Controller が薄く、ビジネスロジックがサービス層に置かれているか

## testing.md（テスト方針）

- [ ] **TDD**: RED → GREEN → REFACTOR の順で書かれた証跡があるか
- [ ] **正常系・異常系・境界値** の3観点を網羅しているか
- [ ] **列挙定数の網羅**: ホワイトリストや列挙の各要素について個別テストがあるか
- [ ] **PHPUnit アトリビュート**: `#[TestDox()]` / `#[CoversClass()]` / `#[DataProvider()]` がプロジェクト標準として付与されているか（PHPUnit プロジェクトの場合）
- [ ] **モック方針**: 外部API = fake / DB = 実 DB / Redis = FlushesRedis / S3 = FlushesS3 / 時刻 = Carbon
- [ ] **テスト間の依存禁止**: `@depends` 等で順序依存を作っていないか
- [ ] **1テスト1アサーション** を基本としているか
- [ ] **`assertSame()` を主軸** に厳密な型・値の一致を検証しているか
- [ ] **テストの説明**: `#[TestDox()]` に日本語で「何を・どうしたら・どうなるか」を記述しているか

## security.md（セキュリティ）

- [ ] **シークレットがコードに直接書かれていないか**（環境変数経由か）
- [ ] **SQL がプレースホルダを使っているか**（直接結合していないか）
- [ ] **HTML 出力時のエスケープ** が行われているか
- [ ] **ファイルパス入力にトラバーサル対策** があるか
- [ ] **エラーメッセージにスタックトレース・内部パス・スキーマ** を含めていないか
- [ ] **認証エラーで詳細を返していないか**
- [ ] **OWASP Top 10** 該当箇所がないか（インジェクション・XSS・XXE・アクセス制御等）

## file-operations.md（ファイル操作）

- [ ] **復元不可能な削除を不用意に行っていないか**（`git rm`・ゴミ箱・退避ディレクトリへの mv を優先しているか）
- [ ] **Makefile / スクリプト内の既存 `rm` をユーザー確認なしに変更していないか**

## git-workflow.md（Git ワークフロー）

- [ ] **コミットメッセージのフォーマット**: `<Prefix>: <日本語タイトル> #<番号>` になっているか（コミットがある場合）
- [ ] **`CLAUDE.md` がコミット対象に含まれていないか**
- [ ] **push 禁止ブランチへの push** がないか（main / master / develop / YYYY-MM-DD / staging / production）
- [ ] **force push / revert / git reset / git config 変更** がないか
- [ ] **PR タイトルが Issue タイトルと一致** しているか（PR がある場合）

## 確認方法

各項目を Verifier が確認する手順:

1. Implementer が変更したファイルを Read で全文確認
2. 上記チェックリストを項目ごとに照合
3. 該当する rules ファイルのセクションを Read で参照（要約禁止）
4. 違反があれば `path:line` と `rules/{file}.md §{section}` の両方を示す

## 適用範囲

- **新規変更箇所のみ** に適用する（既存コードの全項目チェックはスコープ外）
- ただし、新規変更が既存の違反パターンを**複製・拡大**している場合は指摘対象とする
