# Wave 0: 設計契約書の作成ガイド

全構成共通。Wave 1 開始前に conductor が**インターフェース契約書**を作成する。並行実装のモジュール境界不整合を防ぐため、型レベルだけでなくセマンティクスレベルの合意を取る。

## 契約書に含める内容

1. **Base commit SHA** — 作業の起点となる commit hash を必須記載。共有ツリー（既定）では impl が着手前に HEAD がこの SHA と一致するかを検証し、worktree 分離構成ではこの SHA を worktree の基点とする。ブランチ分岐元の誤認による機能誤削除を防ぐ。`git rev-parse HEAD` で取得し `Base commit SHA: abc1234...` の形式で先頭に記載する
2. **エンティティ関係図** — 主要な構造体/型の関係と ID の流れ
3. **モジュール境界の API** — impl 間の呼び出しインターフェース（関数シグネチャ + 戻り値の意味）
4. **データフロー** — イベントがどの順序でどのモジュールを通るか
5. **共有型の定義場所** — どの型をどのモジュールに置くか、重複定義を避ける割当表
   - **消費側の型から逆算する**: 定数・設定値の構造を新規に決める前に、消費側（利用側）が期待する既存型をそのまま使えないか確認する。「データ定義側から決める」のではなく「利用側が求める型に合わせる」ことで変換ロジックの混入と型変更時の追従漏れを防ぐ
6. **呼び出し元・消費者の網羅リスト** — 変更対象の関数・CLI verb・ガード述語について、呼び出し元を **ast パース（または複数行対応 grep）で全列挙**する。CLI verb・公開 API を変更する場合は、workflow スクリプト・cron・他リポジトリ等の**コード外消費者**も影響範囲に含める（削除済み CLI verb を workflow スクリプトが呼び続けて実行時破綻した事例がある）。ガード・遷移述語は「定義されている」だけでなく「**呼び出し側で強制されているか**」を確認する（定義だけで呼ばれない述語は骨抜き）
7. **文字列トークンの正規語彙** — モジュール間・impl/test 間で受け渡す列挙値・トークン文字列は、型定義だけでなく**正確な値レベルで契約書に固定**する（`spec_missing` vs `spec` のようなドリフトで完全一致テストが全滅した事例がある）
8. **コミット順序** — 複数コミットに分ける場合、担当ファイル間の **import グラフを矢印で図示**し、「依存される側が先」の機械的ルールで順序を導出する。契約書に数値表を載せる場合は conductor が検算してから確定する

## 手順

0. **検証環境健全性ゲート** — 契約書作成前に既存テストスイート・依存サービス（テストDB、localstack 等）が緑であることを確認する。壊れていたら実装に着手せず、復旧またはユーザー相談を先に行う（テストDB破損に気づかず検証未完のまま PR が進行した事例がある）
1. conductor がタスクを分析し、上記項目の契約書を作成
2. 契約書を `/tmp/orchestra-{team-name}/design-contract.md` に保存
3. **architect エージェント**（`architect.md`）を spawn し、契約書の評価を依頼する。spawn 時のプロンプトは `agent-prompts.md` の **Architect Review Prompt** を使用する（外部整合性に加えて**内部整合性**——擬似コード実行順序・型定義の妥当性・宣言と実装の一致・テスト方針の実行可能性——を検証する観点を含める）
4. architect の指摘を反映して契約書を改善（最大2回のレビューループ）
5. impl への spawn 時に契約書のパスを渡し、参照を義務付ける

## ファイル割当表

契約書には **担当ファイルの割当表**（ファイルパス → 担当 impl）を必ず含める。1 ファイルは 1 impl に帰属させ、同一ファイルの編集権は割当された impl のみが持つ。
