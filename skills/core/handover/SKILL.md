# Handover（セッション引き継ぎ）

現セッションの作業状況を要約し、次セッションが即座に継続できるドキュメントを生成する。

## 基本原則

1. **含める / 除外する情報を分ける**
   - 含める: タスク概要・ファイルパス・Issue/PR 番号・公開済みコミットハッシュ・残タスク・次アクション・下した判断と理由
   - 除外: `.env` の値・API キー・トークン・個人識別情報・社外秘の内部データ
   - **セッションを跨ぐと無効になる情報**（サブエージェント ID・scratchpad の一時ファイル・実行中プロセス）は原則書かない。言及が必要なら「次セッションでは無効」と明記する（無効な参照の追跡によるコンテキスト浪費を防ぐ）
2. **保存のみ実行する** — `git commit` / `git push` はこのスキルでは実行しない
3. **保存パスと命名規則は固定** — `~/.claude/handovers/{project-name}/{YYYY-MM-DD}_{summary}.md`（実体配置）
   - `{summary}` は英語 kebab-case 2〜5語（例: `login-refactor-phase1-verification`）。日付形式を `YYYYMMDD` 等に崩さない。同日衝突は `_02` サフィックス
4. **往復を増やさない** — handover はコンテキスト逼迫時に起動されることが多く、事前承認の1往復もコストになる。保存は可逆なので、生成 → 保存 → 自己検証 → 提示まで一気に進め、修正依頼には保存後の Edit で応じる
5. **新たな大きな読み込みをしない** — 材料は会話履歴と軽量 git コマンドから得る。長大ファイルの再 Read は、handover 自体がコンテキストを圧迫する本末転倒になるため行わない

## Phase 1: 情報収集（並列実行）

以下を **同一メッセージ内で並列発行** する：

```bash
pwd
git status --short
git diff --stat && git diff --cached --stat
git log --oneline -5
git rev-parse --abbrev-ref HEAD
ls -t ~/.claude/handovers/{project-name}/ 2>/dev/null | head -3
```

会話履歴から抽出する: 触ったファイル（git 出力と突合）/ Issue・PR 番号 / 下した判断と理由 / ユーザーの決定・制約（発言に近い形で）/ 試して捨てた案と理由 / 完了した作業と残タスク / ユーザー確認待ちの事項。

直近の handover が同一タスクの続きなら、新ドキュメントの冒頭に前回のパスを記載してチェーン化する。

## Phase 2: 生成・保存

`mkdir -p ~/.claude/handovers/{project-name}/` の後、以下のテンプレートで Write する。**該当がないセクションは丸ごと省略する**（空見出しを残さない）。

```markdown
# セッション引き継ぎ: {タスク概要}

**作成日時**: {YYYY-MM-DD HH:MM}
**プロジェクト**: {project-name}
**ブランチ**: {current-branch}（HEAD: {short-hash}）
**前回の引き継ぎ**: {path}（継続タスクのみ）

## タスク識別子
- Issue: #{issue-number} / PR: #{pr-number}

## 完了した作業
- {どのファイルのどの関数まで、など具体的に}

## 残タスク
- [ ] {未完了の作業。優先順}

## 次のステップ
1. {次セッション冒頭の一手。読むべき SSOT があれば先頭に}

## 検証手段
- {完了確認に使うコマンド（rules/testing.md の検証手段テーブルから）}

## ユーザー確認待ち・未解決の疑問
- {回答・判断を待っている事項}

## 重要な判断・コンテキスト
- {下した判断と理由。同じ検討の繰り返しを防ぐ}
- {ユーザーの決定・制約・好みは、要約せず発言に近い形で残す（例: ユーザー発言「〇〇は今回は触らない」）}

## 試して捨てた案
- {試した・検討したが採用しなかった案と、その理由。次セッションで同じ案を再試行しないため}

## 関連ファイル
- {path/to/file} - {変更内容の要約}
```

## Phase 3: 自己検証（必須）

保存したファイルを Read で読み返し、以下を確認する。問題があれば Edit で修正してから次へ進む。

```bash
# 1. 変更ファイルの網羅リスト（unstaged / staged / untracked すべて）
{ git diff --name-only; git diff --cached --name-only; git ls-files --others --exclude-standard; } | sort -u

# 2. 秘密情報パターンの混入チェック（保存済みファイルに対して実行）
grep -nE '(API[_-]?KEY|SECRET|TOKEN|PASSWORD|BEARER)[[:space:]]*[=:][[:space:]]*[A-Za-z0-9_\-/+=]{8,}' {保存ファイルパス}
```

- 1 のうち**このセッションで触れたファイル**が「完了した作業」または「関連ファイル」に登場するか（漏れがあれば追記）。他セッション由来の dirty ファイルは対象外（必要なら「本セッションの変更ではない」と注記）
- 2 がヒットしたら該当値を `(redacted)` に置換
- 「関連ファイル」セクションの各パスが実在するか（`ls` でまとめて確認）

## Phase 4: 提示と再開案内

引き継ぎの要点（タスク概要・残タスク・次ステップ）を本文で提示し、修正依頼があれば Edit で反映する。末尾に再開方法を案内する：

```
保存しました: ~/.claude/handovers/{project-name}/{filename}.md

次セッションでは以下で再開してください:
「前回の引き継ぎを読んで作業を続けてください: ~/.claude/handovers/{project-name}/{filename}.md」
```

## 次セッションでの再開時の検証

引き継ぎドキュメントを読んで作業を再開するときは、**記載内容と実際の実装状況のズレを最初に検証する**。

- 前セッション末期の駆け込みコミットなどで、実装が引き継ぎの記載より先行している場合がある（「未着手」と書かれていても既に実装済み、など）
- 次のアクションを開始する前に、以下のいずれかで現状を必ず確認してから差分を整理する:
  - `ls -la`（ファイルの更新日時）
  - CLI の `--help` 出力（実装済みのオプション・サブコマンドの確認）
  - テスト実行（パスする範囲から実装の到達点を把握）
  - `git log --oneline` / `git status`（直近のコミットと作業ツリーの状態）
- 記載を鵜呑みにして重複実装・手戻りを起こさない。記載と現状が食い違ったら、現状（客観的な証拠）を優先する

## Pitfalls

### SKILL.md 本文にドル記号付き位置変数を書かない

- **症状**: 引数付きで Skill 起動すると、本文コード例内のドル記号 + 数字（awk の位置変数等）が引数の単語に置換され、コマンドが壊れる（本スキルの網羅チェック awk が実際に破壊された事例がある）
- **Why**: スキル本文はロード時に引数置換処理を受け、コード例も対象になる
- **ルール**: awk の位置変数が必要な処理は `git ls-files --others` のような代替コマンドで回避するか、references/ 配下のスクリプトに逃がす

## ログ記録

- 保存成功時: `~/.claude/hooks/skill-log.sh handover SAVED "{project} {filename}"`
- 秘密情報を redact した時: `~/.claude/hooks/skill-log.sh handover REDACTED "{project} {検出パターン}"`
- 網羅漏れを追記した時: `~/.claude/hooks/skill-log.sh handover COVERAGE_FIXED "{project} 追記{N}件"`
- エラー時: `~/.claude/hooks/skill-log.sh handover ERROR "{内容}"`
