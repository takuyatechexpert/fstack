# NFD（Nurture-First Development）アーキテクチャ設計書

## 概要

Claude Code エージェントの知識管理を **三層構造** に分離し、「使い込むほど賢くなる」エージェントを実現するためのアーキテクチャ。

従来のように CLAUDE.md にあらゆる情報を集約するのではなく、情報の性質に応じて適切な層に配置することで、コンテキスト爆発を防ぎつつ学習効果を最大化する。

---

## 三層構造

```
┌─────────────────────────────────────────────┐
│  Constitutional Layer（憲法層）              │
│  ~/.claude/CLAUDE.md                        │
│  常に・無条件に・例外なく適用される制約       │
│  コンテキストの 10〜15% 程度に収める         │
├─────────────────────────────────────────────┤
│  Skill Layer（技能層）                       │
│  ~/.claude/skills/*/SKILL.md                │
│  特定のゴールに対する再現可能な手順           │
│  呼び出された時のみコンテキストに読み込まれる │
├─────────────────────────────────────────────┤
│  Experiential Layer（経験層）                │
│  ~/.claude/projects/.../memory/*.md         │
│  過去の決定・失敗・パターンの蓄積             │
│  関連する記憶のみ選択的にロードされる         │
└─────────────────────────────────────────────┘
```

### 情報の流れ

```
グラウンディング（下から上）
  憲法層の原則が、新しい経験を解釈する土台となる
  例: 「不確実な場合は質問する」→ 経験層の記録時にも背景を明確化

結晶化（上から下）
  経験層のバラバラの記録からパターンを抽出し、技能層に昇華させる
  例: 同じレビュー指摘が3回続く → skills/review-pr/references/ にルール追加

淘汰（定期メンテナンス）
  陳腐化した記憶を削除・更新し、経験層の鮮度を保つ
```

## 各層の設計

### 1. Constitutional Layer（憲法層）

**ファイル**: `~/.claude/CLAUDE.md`

**配置基準**: 以下の3条件を **すべて** 満たすものだけを書く

1. **常に適用** — 特定のスキルやタスクに限定されない
2. **無条件に適用** — 文脈による判断が不要
3. **例外なく適用** — 上書きされることがない

**適切な例**:
- コミットは明示的に指示されるまで行わない（常に・無条件・例外なし）
- 不確実な場合は質問で明確化してから実行（常に・無条件・例外なし）
- LSP を Grep より優先する（常に・無条件・例外なし）

**不適切な例**:
- PR レビューでは DDD 階層を確認する → `skills/review-pr/` へ
- テストでは DB をモックしない → `memory/feedback_*.md` へ
- 来週リリースフリーズがある → `memory/project_*.md` へ

### 2. Skill Layer（技能層）

**ディレクトリ**: `~/.claude/skills/`

#### 粒度の原則: 1スキル = 1ゴール

```
❌ 細かすぎ: fetch-pr-info/, parse-diff/, format-review/
❌ 粗すぎ:   all-github-operations/
✅ 適切:     review-pr/（PRレビューという1つのゴール）
```

**判断基準**: 「ユーザーが一言で依頼できる単位」がスキルの粒度。
「PRレビューして」→ 1スキル。「PRのdiffを取って」→ スキルではなくステップ。

#### 命名規則

- **動詞-名詞** の kebab-case で統一（例: `review-pr`, `check-milestones`）
- オーケストレーター型は名詞のみも可（例: `secretary`）

#### ディレクトリ構成

```
skills/
└── {skill-name}/
    ├── SKILL.md              # ワークフロー定義（必須）
    └── references/           # 大きな参照データ（任意）
        ├── checklist.md
        └── rules.md
```

#### 参照ルール

スキル内で参照データを使う場合、**要約やメモリからの再現は禁止**。
サブエージェントにも参照ファイルのパスを渡し、直接 Read させる。

```markdown
## 参照ファイル（絶対パス）
実行時に必ず Read で読み込むこと。要約やメモリからの再現は禁止。
- **チェックリスト**: `~/.claude/skills/xxx/references/checklist.md`
```

### 3. Experiential Layer（経験層）

**ディレクトリ**: `~/.claude/projects/.../memory/`

#### 記録の種類（auto-memory のタイプに準拠）

| タイプ | 用途 | 例 |
|---|---|---|
| `feedback` | 判断ルール・修正指示 | 「DB をモックしない。理由: 本番 migration 失敗の前例」 |
| `user` | ユーザーの知識・好み | 「Go に精通、React は初めて」 |
| `project` | プロジェクトのコンテキスト | 「3/15 リリースフリーズ」 |
| `reference` | 外部リソースへのポインタ | 「バグ管理は GitHub Issues の該当リポジトリ」 |

#### 記録フォーマット（feedback タイプ）

```markdown
---
name: {記憶名}
description: {一行の説明}
metadata:
  type: feedback
---

{ルール・制約の記述}
**Why:** {この判断に至った理由・失敗の経験}
**How to apply:** {いつ・どこで適用するか}
```

#### ログと記憶の区別

```
ログ（生データ）                    記憶（蒸留されたルール）
~/.claude/logs/skills.log         memory/feedback_*.md
~/.claude/skills/*/log.md         memory/project_*.md

[例] APIレスポンスの                APIレスポンスは BaseResponse で
エラー形式が混在していた           統一する
                                   Why: フロントの例外処理共通化
                                   How to apply: API実装時に常に適用
```

**ログは操作データ、記憶は行動を変えるルール。**
ログに直接判断ルールを書かない。ログから蒸留した結果を記憶として保存する。

## 結晶化ワークフロー

経験層から技能層へ知識を昇華させるプロセス。
NFD において最も重要なサイクル。

### 実行タイミング

- **推奨**: 週次（金曜午後に30分）
- **トリガー**: `/crystallize` スキルで実行

### ワークフロー

具体的な実行手順は `~/.claude/skills/crystallize/SKILL.md` を単一の真実のソースとする。
（本書に手順を複製すると SKILL.md 改訂時にドリフトするため、本書は思想・判断基準のみを扱う）

### 結晶化の判断基準

| 段階 | 条件 | 配置先 |
|---|---|---|
| 観察 | 初回の気づき | ログに記録（memory には入れない） |
| 記憶 | 2回以上発生 or ユーザーが明示的に指示 | `memory/feedback_*.md` |
| 結晶化 | 1ヶ月以上安定して適用されている | `skills/*/references/` |
| 憲法化 | 全スキル・全タスクに例外なく適用 | `CLAUDE.md`（極めて稀） |

## 対話的没入（日常の育成）

結晶化を効果的にするため、日常の対話で以下を意識する。

### 推論トレースを求める

エージェントがコードを提案した際に理由を問いかける。

```
✅ 「なぜそのライブラリを選んだのか？」
✅ 「なぜその実装パターンにしたのか？」
✅ 「他の選択肢と比較した結果は？」
```

### 修正に理由を添える

単に「直して」ではなく、判断の根拠（暗黙知）を言語化して伝える。

```
❌ 「ここ直して」
✅ 「このプロジェクトではセキュリティのために XX という書き方を
    徹底しているから、次からはこうしてほしい」
```

これにより `feedback` タイプの記憶として自動蓄積される。

|---|---|
| 導入時 | CLAUDE.md が憲法層として最小化されている ✅ |
| | skills/ にワークフローが定義されている ✅ |

| 1ヶ月後 | 最初の結晶化を実施し、skills/ に 2〜3件のルールが追加されている |

## アンチパターン

| アンチパターン | 問題 | 対策 |
|---|---|---|
| CLAUDE.md に手順を書く | コンテキスト肥大化 | skills/ に移す |
| スキル内で参照データを要約して渡す | 情報劣化・ハルシネーション | ファイルパスを渡し Read させる |
| memory にログを直接書く | ノイズが増え検索性が低下 | ログと記憶を分離する |
| 1スキルに複数ゴールを詰め込む | 呼び出し判定が曖昧になる | 1スキル1ゴールに分割 |
| ログを残して memory に昇格させない | 同じミスを繰り返す | 週次の結晶化を実施する |
| 陳腐化した記憶を放置する | 誤ったルールが適用される | 結晶化時に淘汰も行う |

## 既存システムとの関係

### auto-memory（Claude Code 組み込み）

Claude Code は会話中に自動的に `memory/` にファイルを作成する。
NFD はこの仕組みをそのまま活用し、**追加のファイル（memory.md 等）は作成しない**。

### hooks ログ

`~/.claude/logs/` に集約されるログは、結晶化の **入力データ** として機能する。
ログ収集（hooks）→ パターン抽出（crystallize）→ 記憶蓄積（memory/）の流れ。

### skills/ ディレクトリ（既存スキル群）

既存スキルの構成変更は不要。結晶化で得られたルールを `references/` に追記していく。
