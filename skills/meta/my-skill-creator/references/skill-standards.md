# Skill Standards（スキル構築の基準）

Claude Code 用スキルがどうあるべきかの **単一の真実のソース**。
my-skill-creator（新規作成）と skill-auditor（健康診断）の両方がこのファイルを基準として参照する。
基準を変更したい場合はこのファイル**だけ**を更新すること。

---

## スキルの配置先

```
~/.claude/skills/{skill-name}/
```

dotfiles リポジトリ等で別管理している場合は、実体パスが `~/.claude/skills/` にシンボリックリンクされている前提で扱う（fstack の setup スクリプトもこの方式を採用）。

## スキルの構成

```
{skill-name}/
├── SKILL.md          （必須）
├── scripts/          （任意: PTC用スクリプト。Bashから呼び出す実行ファイル）
├── references/       （任意: 詳細情報。SKILL.md が 500行を超えたら分離を検討）
└── assets/           （任意: 出力に使うテンプレートや素材）
```

- 不要なファイル（README.md, CHANGELOG.md等）は作らない
- `references/` は自動読み込みされない。SKILL.md から参照して初めてロードされる

## SKILL.md の構造

### フロントマター（YAML・必須）

```yaml
---
name: {kebab-case-name}
description: {日本語で機能説明 + トリガーフレーズ}
---
```

**description の書き方:**
- 何をするスキルか + 「ユーザーが〇〇と言ったときに使用する。」でトリガーを明示
- Claude はスキルを**使わない方向に傾きがち**なので、トリガーフレーズは少し広めに書く
- 「〜したい」「〜して」「〜確認したい」など複数パターンを含める

### model / effort の判断軸（任意フィールド）

`model` / `effort` は性能とコストのトレードオフを決めるフロントマター。特定モデルへのピン留めは最小限にする。

**model:**

| 種別 | 設定 | 対象 |
|---|---|---|
| 推論系 | 行を書かない（inherit） | 深い推論が品質に直結するもの。設計判断・コードレビュー・並列実装オーケストレーション・分析・ナレッジ蒸留（例: orchestra-of-agents, solo-with-verifier, review-pr, crystallize, skill-auditor） |
| 機械的定型処理 | `model: haiku` / `model: sonnet` 固定 | チャット投稿・定型申請・UI 自動操作・情報取得＆表示など。上位モデルはオーバースペック |
| 採点・評価系 | モデル固定を維持 | ベンチマーク比較可能性のため。採点者のモデルを変えると過去結果と比較できず劣化検出が壊れる |

- inherit にするとセッションのモデル（最上位含む）にそのまま追従する
- **特定モデルのピン留めはリスク**: 指定モデルが利用プランで使えない場合、フォールバックせずエラーになる可能性がある。`fallbackModel` チェーンは可用性エラー専用で、無効モデル指定時の挙動は保証されない

**effort:** セッションのデフォルト effort は高めのため、推論が軽くて済むスキルに `effort: high` を付けて下げる。

- **付けない（デフォルト維持）**: 深い多段推論が品質に直結するもの（推論系と同じ顔ぶれ）
- **`effort: high`**: 定型ワークフロー・UI 自動操作・情報取得＆表示・投稿・申請（例: handover）
- **制約**: effort はモデル依存。`model: haiku` 指定スキルには付けない（モデルで軽量化済み）。`model: sonnet` は実質 high が上限のため付与しても挙動はほぼ変わらない。実質的に効くのは inherit / 上位モデル指定のうち軽いもの
- **書式**: フロントマター閉じ `---` の直前、`model:` があればその下に 1 行 `effort: high`

### 本文（Markdown）

```markdown
# {スキル名}
{1行の概要}

## 参照ファイル（references/がある場合）
## ワークフロー
### Phase 1: ...
### Phase 2: ...
## ログ記録
## 注意事項
```

## 設計原則

### 1スキル = 1責務

スキルのスコープは「関数」くらいの粒度で設計する。
1つのスキルが複数の無関係な責務を持つと、トリガー判定が曖昧になり、SKILL.md も肥大化する。

**適切なスコープの判断基準:**
- description を1文で書けるか？ → 書けないなら分割を検討
- 「AかつB」ではなく「AまたはB」で発動するか？ → 別スキルにすべき
- 他スキルと組み合わせて使う想定か？ → ベーススキルとして切り出す（例: `slack` スキル）

**過大の兆候:** description に「〜も〜も」が3つ以上、SKILL.md が 500行超
**過小の兆候:** 毎回他のスキルとセットでしか使われない

### 簡潔さ優先

Claude が既に知っていることは書かない。SKILL.md は **500行以内かつ5000トークン以内** を目安。
日本語は1文字≒1.5トークンのため、英語より早くトークン上限に達する。行数に余裕があってもトークンで溢れることがある。
冗長な説明より簡潔な例を使う。

### MUSTより "why" を説明する

強制的なルールより、なぜそうするかの理由を書く方が効果的。
モデルは理由を理解した上で状況に応じた判断ができる。

### 自由度の設定

| 自由度 | 使い分け | 記述方法 |
|---|---|---|
| 高 | 複数アプローチが有効、文脈依存 | テキスト指示 |
| 中 | 推奨パターンあり、多少の変動OK | 擬似コード・パラメータ付きスクリプト |
| 低 | 手順の正確さが重要、エラーに弱い | 具体的なコマンド・スクリプト |

### 落とし穴（Pitfalls）セクション

対象ドメイン固有の「AIが知らないと確実にハマる暗黙知」をスキルに明記する。
コードやドキュメントを読んだだけでは分からない罠ほど価値が高い。

新規作成時はユーザーに「このドメインでAIがハマりそうな罠はあるか？」を必ずヒアリングする。
既存スキルの健康診断時も、Pitfalls は**実体験ベースのみ採用**する（未発生の一般論は追加しない）。
各項目は **症状 / Why / ルール** の形式で記述する。

**良い落とし穴の例:**
- `users` テーブルは論理削除。クエリには `where deleted_at is null` が必須
- ユーザーIDはDBでは `user_id`、認証では `uid`、課金では `accountId`
- `/health` は常に200を返す。実際の死活判定は `/health/ready` を使う

**落とし穴にならないもの（書かなくてよい）:**
- 公式ドキュメントに明記されている仕様
- コードを読めば自明なこと

### Progressive Disclosure

1. **メタデータ（name + description）** — 常にコンテキストに存在（トリガー判定用）
2. **SKILL.md 本文** — トリガー後にロード
3. **references/** — Claude が必要と判断したときにロード

### PTC（Programmatic Tool Calling）

3つ以上の独立した外部呼び出しを並列化する場合、Python スクリプトで Bash から呼ぶパターン。
詳細は `~/.claude/skills/my-skill-creator/references/ptc-pattern.md` を参照。

### 出力フォーマットの定義

スキルが構造化された出力を返す場合、期待するフォーマットを SKILL.md に明示する。
Claude に毎回フォーマットを「発明」させると、実行ごとにブレが生じる。

**定義すべきケース:**
- Slack 投稿・GitHub コメントなど、人が読む定型出力
- JSON/YAML など、後続処理が消費する構造化データ
- Markdown テーブル・レポートなど、見た目の一貫性が必要なもの

**定義方法:** テンプレートを SKILL.md 内にインラインで書くか、`assets/` に配置して参照する。

```markdown
## 出力フォーマット
\`\`\`
【{カテゴリ}】{タイトル}
状態: {status}
担当: {assignee}
\`\`\`
```

**検証ループ:** フォーマットを定義したら「作業 → 出力 → フォーマット照合 → 修正」のループを Phase に組み込む。

### ログ記録（デフォルト）

全スキルにログ記録セクションを含める。共通ヘルパースクリプトを使用する:

- **起動ログ**: PostToolUse (Skill) hookが自動記録するため、スキル側での記述は不要
- 成功時: `~/.claude/hooks/skill-log.sh {skill-name} TAG "{実行時間}s ..."`
- エラー時: `~/.claude/hooks/skill-log.sh {skill-name} ERROR "{エラー内容}"`

実行時間は `date +%s` で開始時刻を記録し、終了時に経過秒を計算する。
ログが不要な場合は明示的に省略理由を記載する。

**ログ粒度:** 単一タグで `success|failed` のような雑な記録は避け、分岐ごとに独立タグを割り当てる。
事後に `grep` だけで分類・集計できる粒度を目標とする。

### eval 基盤（品質保証）

客観的に検証できる出力を持つスキルには eval を設定する。
eval がないスキルは劣化検出ができないため、健康診断（skill-auditor）では Step 1 で eval 基盤構築を**必須化**している。

- `evals/evals.json` にテストプロンプトを複数件
- `evals/expectations.json` でアサーション（**trivially pass を避ける**: 見出し存在だけでなく実データ内容・負のアサーション・境界値も含める）
- ベースライン pass_rate を記録し、以降の変更で**劣化していない**ことを確認する

詳細は `~/.claude/skills/my-skill-creator/references/eval-workflow.md` を参照。

### description 最適化（トリガー精度）

誤発火・取りこぼしを定量的に潰すため、以下を行う:

- `evals/trigger-eval.json` に should_trigger 20件 / should_not_trigger 20件（near-miss 重視）
- Recall / Precision 双方 ≥ 90% を目標
- NOT 条件（「以下では起動しない: ...」）を description に明記し、競合スキル領域を除外

詳細は `~/.claude/skills/my-skill-creator/references/description-optimizer.md` を参照。

### design/ ディレクトリの運用

- `design/` には原則 `IMPROVEMENT-PLAN.md` のみを置く
- 実装前の SPEC 等を置いてもよいが、**実装完了後は SKILL.md / references が真実のソースになるため SPEC は削除**する
- 二重管理は基準ドリフトの温床

## 検証チェックリスト（新規作成・更新時の最終確認）

- [ ] SKILL.md フロントマターに `name` と `description` がある
- [ ] description にトリガーフレーズが十分含まれている（少し広め）
- [ ] `model` / `effort` を判断軸に沿って設定（推論系は inherit、機械的定型は haiku/sonnet 固定、評価系は固定維持）。不要なピン留めをしていない
- [ ] description に NOT 条件が書かれている（競合スキル・誤発火領域の除外）
- [ ] SKILL.md が 500行以内かつ5000トークン以内（`bash ~/.claude/skills/my-skill-creator/scripts/count-tokens.sh <SKILL.md>` で確認）
- [ ] references/ の個別ファイルが 500行以内
- [ ] 1スキル = 1責務（description を1文で書ける）
- [ ] Pitfalls セクションがある（実体験ベース + Why + ルール）。該当する実事故がなければ省略可
- [ ] ログ記録セクションがある（不要な場合は理由を記載）
- [ ] ログ粒度が分岐ごと（単一タグで雑に済ませていない）
- [ ] `~/.claude/skills/` 経由でアクセスできる（シンボリックリンク確認）
- [ ] 客観的に検証可能な出力がある場合、eval を設定し with_skill の pass_rate がベースラインとして記録されている
- [ ] `design/` に実装済み SPEC が残存していない
